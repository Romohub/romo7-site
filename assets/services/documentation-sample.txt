## Findings and proposed clarification

### F1 — Put the caching exception next to the ZDR definition

**Documented fact:** S1 opens with a broad no-storage definition, then explicitly allows implicit prompt caching in provider memory under its ZDR classification. It also excludes enabled plugins and tools from inference-routing ZDR enforcement.

**Finding:** The introductory definition is broader than the later caching exception. A reader who stops at the definition could interpret ZDR as eliminating every temporary copy. That reader effect is an inference; this review does not establish noncompliance or provider misconduct.

**Suggested clarification:** “ZDR routing selects inference endpoints classified as having no retained prompt or completion data. This classification permits implicit in-memory prompt caching. Enabled tools and plugins have separate retention policies.”

**Recheck:** In S1, compare the opening definition with Caching, then check the tool exclusions immediately below the opening paragraph. The proposed copy must preserve both exceptions.

### F2 — Add a parameter-support warning to the fallback quickstart

**Documented fact:** S2 explains automatic model failover. S3 states that `require_parameters` defaults to `false`; unsupported parameters may be ignored. For `response_format`, provider preferences do not eliminate an entire fallback model when none of its providers supports the parameter.

**Finding:** The fallback quickstart does not locally explain this parameter-support caveat. A developer can add a fallback without realizing that required response formatting needs a separate routing constraint. This is a cross-reference improvement, not evidence that a request failed.

**Suggested clarification:** “If every fallback must support your requested parameters, set `provider.require_parameters` to `true` and choose compatible models. Otherwise unsupported parameters may be ignored; a fallback list alone does not require parameter compatibility.”

**Recheck:** Search S3 for `require_parameters` and the following Default parameter preferences section; compare that explanation with S2's failover quickstart. No live response-format validation was performed.

### F3 — Qualify the pooled budget example with BYOK accounting

**Documented fact:** S4 introduces workspace budgets as pooled spend caps. Its later BYOK section says guardrails normally count credit spend, workspace and guardrail BYOK switches are separate, and recorded BYOK inference cost may differ from the upstream invoice. S5 also states that a key's `include_byok_in_limit` default is `false`.

**Finding:** The pooled-cap example can be read as covering the whole provider bill before the BYOK conditions are encountered. Add the accounting caveat beside that example. This review does not establish any actual overspend or billing error.

**Suggested clarification:** “These examples cap the spend included by each control. If you use BYOK, enable its accounting separately at the workspace, guardrail and key layers you rely on. OpenRouter's recorded BYOK cost may differ from your provider invoice.”

**Recheck:** Compare S4's The Two Layers example with BYOK and Budget Accounting; confirm S5's key toggle default. Do not describe the cap as an exact ceiling on an external provider invoice.
