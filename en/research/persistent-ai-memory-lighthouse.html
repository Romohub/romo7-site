AI Agents Don’t Just Need Bigger Context Windows. They Need Memory That Survives the Session.

Published 6 October 2026 · Hands-on research note

A lot of the current conversation about AI agents focuses on model quality: better reasoning, larger context windows, stronger tool use, cheaper inference. Those things matter. But while building workflows that are supposed to keep going across sessions, I kept running into a more basic problem: continuity.

An agent can be excellent inside one session and still become frustrating the moment the process restarts, a device disconnects, or a different client takes over. The model may be smart, but the workflow has amnesia.

That led me to test Lighthouse Memory, a memory layer designed around three explicit actions: remember, recall, and forget.

The experiment

I wanted a test that reflected a real workflow rather than a toy preference like “the user likes dark mode.” My actual requirement is this:

When the computer disconnects, continue cloud-safe research and resume device-dependent work after reconnection without asking the user to repeat the task.

I installed the official Lighthouse Memory SDK and used its batched engine with the local filesystem storage adapter. In one Node process, I called remember() with that workflow rule and forced immediate flushing. The SDK produced a content-addressed identifier (CID):

bafkreigkv56ttjnoijmstxekifmyhg7har7mbyqcssmpsr6wo3r4hmpauq

Then I ended that process. In a separate process, with no chat transcript carried over, I asked the memory layer: “What should the agent do if the computer disconnects?”

It returned the stored rule and the same CID.

This was a local-adapter test, so it does not prove decentralized network persistence. What it does demonstrate is the core behavior of Lighthouse’s SDK: state can live outside the active model process and be recovered by a later runtime.

Context is not the same thing as memory

A context window answers: “How much information can the model consider right now?” Persistent memory answers: “What useful information should still exist after this runtime is gone?” Those are different engineering problems.

You can make a context window enormous and still lose continuity when you start a fresh session. You can also keep dumping old transcripts into prompts, but that becomes expensive, noisy, and difficult to govern.

An external memory layer gives the agent explicit operations: store something worth keeping, retrieve related information later, and remove information that should no longer be retained.

What Lighthouse adds beyond my local test

Lighthouse documents its memory system as composable. The same high-level memory interface can use different engines, storage backends, and embedders. Its architecture also exposes memory tools through MCP for compatible AI clients.

The important idea is not “give one chatbot better history.” It is to make memory external to the model so different runtimes can access durable state.

Verifiability is useful, but privacy matters more

Lighthouse uses content-addressed blobs and CIDs. That gives persisted objects identifiers tied to their content, which is useful when provenance matters.

But persistent memory creates a harder question: what should never be remembered? Lighthouse’s documentation makes clear that privacy and deletion semantics depend on the chosen engine and backend. Plaintext storage should not be treated as a safe place for secrets or personal data, and forget() cannot be assumed to rewrite every underlying storage network in the same way.

The useful feature is not maximum retention. It is controlled retention.

The bigger lesson

After this test, I think the AI-agent conversation needs a cleaner separation between intelligence and continuity. A model can reason well and still be operationally unreliable if every new runtime starts from scratch.

A strong external memory layer should provide persistence across sessions and runtimes, relevant retrieval rather than transcript dumping, portability across tools and models, and understandable deletion and privacy rules.

My test was deliberately modest: local storage, two separate processes, one real workflow rule. It worked. The more important next test is the networked version: persist the memory through a remote backend, restore it from another machine or MCP client, and verify the same state there.

That is the point where “AI memory” stops being a convenience feature and starts looking like infrastructure.
